## Workstream 1 — role switching

### Investigation

Read `app/src/App.tsx` and `app/src/components/Sidebar.tsx`. Found two
independent role switchers sharing one piece of state
(`roleOverride`/`setRoleOverride`):

- `Sidebar`'s "Your roles" group — renders whenever `heldRoles.length > 1`
  (a REAL account holding more than one role, from `user_roles`), in
  every build.
- `Sidebar`'s DEMO_MODE "Preview as" grid — renders only in demo builds,
  lets a reviewer force any of the 5 roles regardless of what the
  session actually holds.

`App.tsx` computed the effective role as:

```js
const role: Role = (DEMO_MODE ? roleOverride : null) ?? sessionRole ?? 'teacher';
```

The comment above `roleOverride`'s declaration called it "the demo
switcher and nothing else." That was the wrong mental model: outside
DEMO_MODE (i.e. any production build), the ternary's first branch is
always `null`, so `roleOverride` is never consulted — clicking "Your
roles" changes React state and the screen shows no difference. This
exactly reproduces "clicking another role does nothing" for a real
multi-role account in a production build.

Confirmed in production (Supabase project `wxkxdqwhefezjfmysypa`,
carried over from Phase 2.1's investigation) that `joshua@anhs.test`
genuinely holds `school_admin, registrar, adviser, teacher, student`
(plus `principal`, which has no client-side mapping) via `user_roles` —
so the "Your roles" switcher would render for it in a real deployment.

### Root cause fix

Extracted the derivation into a pure, exported function:

`app/src/nav.ts` — `resolveActiveRole({ demoMode, roleOverride, heldRoles, sessionRole })`:

```js
if (demoMode && roleOverride) return roleOverride;
if (roleOverride && heldRoles.includes(roleOverride)) return roleOverride;
return sessionRole ?? 'teacher';
```

- DEMO_MODE's grid may still force ANY role, held or not (its purpose).
- The "Your roles" switcher may only land on a role `heldRoles` actually
  contains — already all it ever offered a button for; checking here is
  defense in depth and also what makes a stale override safe across a
  sign-out into a different account (a leftover value naming a role the
  new account doesn't hold fails the check and falls through).

`App.tsx` now calls `resolveActiveRole(...)` instead of inlining the
formula.

### Tests added

`app/src/nav.test.ts`, `describe('resolveActiveRole — the multi-role
switch')`, 6 cases: held-role switch outside DEMO_MODE (the regression),
walking all 5 held roles, refusing an unheld role outside DEMO_MODE,
DEMO_MODE still forcing an unheld role, falling back to session role,
falling back to 'teacher'.

**Proved the test catches the regression, not just the fix**: reverted
`resolveActiveRole`'s body to the literal old formula, ran the suite —
2 of 6 new assertions failed exactly as expected. Restored the fix,
re-ran — all 6 (26 total in the file) passed.

### Findings — architecture questions answered

| Question | Answer | Evidence |
|---|---|---|
| Can multiple years coexist? | Yes, always could | `unique(school_id, label)`, never `unique(school_id)`. Inserted a 3rd year (2027-2028, `planning`) alongside the seeded 2026-2027 (`active`) and 2025-2026 (`archived`) — no violation. |
| Can terms belong to a specific year? | Yes, always did | `academic_periods.academic_year_id` FK, `unique(academic_year_id, ordinal)`. |
| Can a year be marked closed/archived? | Yes, always could | `status` CHECK: planning/active/closed/archived. |
| Do historical records survive archiving? | Yes, always did | `app.reject_write_to_archived_year()` refuses writes to rows carrying an archived year's id — even for school_admin — without touching existing rows. `seed.sql` itself creates a prior year, populates enrolment + grade rows, THEN archives it, "exercising the read-only guard" per its own comment. |
| Are archived years still queryable? | Yes | `my_academic_history()` reads `enrollments` by `app.current_student_id()` with no filter on year status. |
| What controls the active year? | `academic_years.status = 'active'` | Read once at session load in `App.tsx`. |
| What controls the active term? | `academic_periods.status = 'active'` | Same session-load effect, within the active year. |
| Why does the app default to a particular term? | Data, not a literal | `App.tsx`: `s.academicYears.find(y => y.status==='active') ?? s.academicYears[0]`, then `active.periods.find(x => x.status==='active') ?? active.periods[0]`. Not persisted browser state, not role state. |

### The one genuine gap found

`rds.session_context()` (`0014_app_data_sources.sql`) returns
`academicYears` **ordered `by y.start_date desc`** and includes each
year's `status`. The client's `AcademicYear` type (`app/src/data/types.ts`)
did NOT include `status` — it was fetched into `SessionYear` and then
dropped on the `App.tsx` mapping into `AcademicYear`.

Two screens defaulted their own year picker to `years[0]` rather than
the active year: `ReportPicker.tsx`, `ConsolidatedGrades.tsx`.

**Confirmed live, not just read**, by inserting a 'planning' SY 2027-2028
(start_date later than the active 2026-2027) into the rebuilt database
and calling `public.session_context()` as `admin@anhs.test`:

```
FIRST YEAR IN LIST (this is what years[0] picks) = {"label": "2027-2028", "status": "planning"}
```

`App.tsx`'s own bootstrap already guards against this
(`.find(active) ?? [0]`); `ReportPicker`/`ConsolidatedGrades` did not
share that logic, so once a school prepares next year ahead of time —
an entirely ordinary registrar action — both screens would silently
default to the future, empty year.

### Fix

- `app/src/data/source.ts` — `SessionYear.status` tightened from
  `string` to `'planning' | 'active' | 'closed' | 'archived'` (matches
  the DB CHECK; `SessionPeriod.status` already had this strictness).
- `app/src/data/types.ts` — `AcademicYear` gains the same `status`
  field, documented.
- `app/src/data/fixtures.ts` — `YEAR_TRIMESTER`/`YEAR_QUARTER` given
  `status: 'active'`; the `academicYears` session mapping now copies
  `y.status` instead of hardcoding `'active'`.
- `app/src/App.tsx` — both `year` and `allYears` `useMemo`s now thread
  `status` through.
- `app/src/screens/ReportPicker.tsx`,
  `app/src/screens/ConsolidatedGrades.tsx` — initial `yearId` state now
  `(years.find(y => y.status === 'active') ?? years[0])?.id ?? ''`,
  matching `App.tsx`'s own pattern. Year `<option>` labels now append
  `(status)` for anything not active, e.g. `SY 2025-2026 (archived)`.

### Tests added

`app/src/nav.test.ts`:
- `describe('academic year administration')` — 'years' route reachable
  only by school_admin; marked `ready` not `planned`; `App.tsx` actually
  has a `case 'years':`.
- `describe('year pickers prefer the ACTIVE year...')` — structural
  source-scan (same technique the file's existing `HANDLED` set uses)
  confirming both `ReportPicker.tsx` and `ConsolidatedGrades.tsx`
  contain the `.find(status active) ?? [0]` pattern. **Proved this
  catches a regression**: reverted `ReportPicker.tsx` to the old
  `years[0]` line, re-ran — the new assertion failed exactly as
  expected; restored, re-ran — passed.
- `describe('the grading-period selector is not hard-coded...')` —
  confirms the topbar's period `<option>` text is built from
  `year.label`/`p.name` (regex match against the literal template in
  `App.tsx`'s source), and that it maps over `year?.periods` rather than
  a fixed list.

## Workstream 4 — Academic Years screen

Built `app/src/screens/AcademicYears.tsx`: read-only. Lists every year
(most recent first, as `session_context()` already orders them) with a
status pill (Active/Closed/Planning/Archived) and a table of its
periods, each with its own status pill. **No new backend call** — built
entirely from `allYears`, which `App.tsx` already computed.

No create/close/archive action. The placeholder's original reasoning
(creating a year decides the shape of everything downstream; archiving
makes it read-only by trigger; it is seeded during onboarding, not
edited live) is unchanged and now appears as copy inside the screen.

Wired: `app/src/App.tsx` imports it and adds `case 'years': return
<AcademicYears years={allYears} />;`. `app/src/nav.ts`'s `years` NavItem
changed from `readiness: 'planned'` (with a `note`) to `readiness:
'ready'` (no note — the explanation lives in the screen now).
`e2e/navigation-audit.mjs`'s `DELIBERATELY_PLANNED` list had `'Academic
Years'` removed, since it is no longer a placeholder; the suite's
generic "opens a real screen, renders content, no console errors, no
duplicate keys" checks now exercise it directly (passed).

**Manual verification**: screenshotted the screen as Administrator in

## Unresolved issues (reported, not changed)

   carrying `academic_year_id` directly (`enrollments`, `classes`).

   (`assessments`/`period_grades`/etc.) are not covered by this
   specific trigger. Currently unreachable — nothing in the app archives
   a year yet (still a direct column update, onboarding-time only) — so
   this is latent, not exploitable. Extending coverage to 6+ more tables
   is out of scope for "the minimum foundation" this phase asked for.

   2.1's report — not re-touched this session, not this session's
